Tutorial: Run SHRAG End-to-End

Hands-on commands for local RAG serving, benchmark execution, fine-tuning readiness flow, and enterprise verification gates.

✅ Prerequisites
RequirementCommand / Value
Python environment.venv with project dependencies installed
Repo rootcd self-healing-rag
State directorymkdir -p .state
ERB path (optional benchmark)ERB_DIR=/path/to/EnterpriseRAG-Bench
🚀 1) Start the RAG API
cd self-healing-rag

# Optional benchmark-friendly limit
export SHRAG_RATE_LIMIT_PER_MINUTE=10000

# Start API
PYTHONPATH=src ./.venv/bin/python -m uvicorn shrag.api.main:app --host 127.0.0.1 --port 8000
Health check:
curl -sS http://127.0.0.1:8000/healthz
curl -sS http://127.0.0.1:8000/v1/healthz
📥 2) Ingest + Query Basic RAG Flow
# Ingest two docs
curl -sS -X POST http://127.0.0.1:8000/docs \
  -H "Content-Type: application/json" \
  -H "X-API-Version: 2026-05-01" \
  -H "X-Tenant-Id: demo-tenant" \
  -H "X-Roles: writer" \
  -H "X-User-Id: demo-user" \
  -d '{"documents":[{"document_id":"doc-1","text":"RAG combines retrieval with generation."},{"document_id":"doc-2","text":"Hybrid retrieval uses dense and sparse search together."}]}'

# Query
curl -sS -X POST http://127.0.0.1:8000/query \
  -H "Content-Type: application/json" \
  -H "X-API-Version: 2026-05-01" \
  -H "X-Tenant-Id: demo-tenant" \
  -H "X-Roles: reader" \
  -H "X-User-Id: demo-user" \
  -d '{"query":"What is hybrid retrieval?","top_k":5}'
🧪 3) Run ERB Benchmark Harness
Env-Driven Benchmark Headers
export SHRAG_ERB_API_VERSION=2026-05-01
export SHRAG_ERB_ROLES=writer
export SHRAG_ERB_USER_ID=erb-bench-runner
export SHRAG_ERB_TENANT_ID=erb-bench
Commands
# Full chain (requires ERB checkout)
make erb-bench ERB_DIR=/path/to/EnterpriseRAG-Bench SHRAG_BASE_URL=http://127.0.0.1:8000

# Or phase-by-phase
make erb-bench-ingest ERB_DIR=/path/to/EnterpriseRAG-Bench SHRAG_BASE_URL=http://127.0.0.1:8000
make erb-bench-eval   ERB_DIR=/path/to/EnterpriseRAG-Bench SHRAG_BASE_URL=http://127.0.0.1:8000
make erb-bench-report
Outputs: .state/erb-ingest-manifest.json, .state/erb-answers.jsonl, .state/erb-results/*, .state/erb-bench-report.json.
🧠 4) Run Fine-Tuning Readiness Lane
# Simulated local lane
make finetune-readiness-simulated

# Inspect generated reports
ls -1 .state/finetune-*.json

# Strict production verification (fails if artifacts are simulated)
make finetune-readiness-production-check
🛂 5) Run Enterprise Release Gates
# Core release gate
make release-gate

# Strict gate with external evidence expectations
make release-gate-strict

# Enterprise audit bundle
make enterprise-readiness-audit-strict
make publish-evidence

🧠 Why SHRAG + H100 Is the Right Split
Fine-Tune Into Model Weights
  • • Enterprise terminology and style
  • • Workflow reasoning and escalation behavior
  • • Tool-usage patterns and structured response formats
  • • Coding and troubleshooting heuristics

🚀 Rollout Process
  • 1
    Introduce new version in allowlist. No traffic change yet.
  • 2
    Add compatibility tests for both old and new versions. Both must pass CI.
  • 3
    Announce migration window. Monitor adoption metrics. After 90-day window, remove old version.
📜 Change Policy
Additive first New fields, new optional parameters — no version bump required.
Breaking changes Require migration notes and dual-read period across both versions.

Security

Threat Model

Assets, trust boundaries, key threats, mitigations, and residual risk.

💎 Protected Assets
  • 🗨️ User prompts and conversation history
  • 📄 Retrieved documents and embeddings
  • 🤖 Model responses and telemetry
  • 🔑 API keys, tokens, and service credentials
🚧 Trust Boundaries
  • → External clients → API gateway
  • → API service → retrieval/index stores
  • → API service → model provider(s)
  • → Observability stack ← operational telemetry
⚠️ Key Threats & Mitigations
Prompt Injection & Retrieval Poisoning High
  • Input validation and policy-enforced tool access
  • Retrieval source validation and signed content pipeline
Data Exfiltration (logs / model output) High
  • Output moderation and PII redaction for sensitive contexts
  • Immutable audit trails — see shrag.security.rtbf
Credential Compromise (CI/CD or runtime) Medium
  • Secret rotation and workload identity
  • Least-privilege IAM, no plaintext secrets in git
Denial of Service (retrieval + generation) Medium
  • Rate limiting and circuit breakers
  • Graceful degradation — smaller context / cheaper model fallback
🕳️ Residual Risk
Open Third-party model behavior drift — no full control over provider updates.
Open Zero-day dependencies — mitigated by dependency scanning but not eliminated.
Open Governance gaps in newly onboarded data sources — connector review required.

Runbooks

Severity-based incident handling, DR procedures, and model rollback.

🔴 Service Degradation
Triggers
Elevated p95/p99 latency Increased 5xx rate SLO burn alert firing
Triage Steps
  • 1
    Validate alert scope — global vs single dependency failure.
  • 2
    Check recent deploys and config changes for correlation.
  • 3
    Inspect retrieval store, model provider, and queue saturation.
Mitigation
  • 1
    Enable degraded mode: smaller context / cheaper model fallback.
  • 2
    Apply traffic shaping and rate limiting.
  • 3
    Roll back latest risky deploy if correlated.
Exit Criteria: Error rate and latency within SLO thresholds. No active fast-burn alerts for 30 minutes.
